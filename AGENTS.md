# AGENTS.md

Short mandatory rules for agents and contributors.
Context and details live in `docs/`. This file is loaded in every
session, so it does not contain the roadmap or long explanations.

## Project

Android port of Simon Tatham's Puzzle Collection.
Game logic is C code from upstream. The project goal is a modern
UI/UX without changing the rules, the seed, or the save format.

## Sources of truth

1. **Game semantics, RNG, seed, save format** — upstream C.
2. **Parity contract** — `docs/PARITY.md`.
3. **Shell design** — `docs/DESIGN.md` and the official Google guidelines.
4. **Architecture decisions** — `docs/adr/`.

When rules conflict, use this order:

> game semantics and save format > accessibility and correctness >
> Google guidelines > visual polish > code style.

If one rule conflicts with another, stop and ask.

## Hard rules

- **Do not edit vendored C.** The file list is
  `app/src/main/jni/UPSTREAM-FILES.txt`; the project-owned exceptions
  are listed in `tools/vendored-project-files.txt`.
- **Do not change the RNG, the meaning of the seed, `DESC`, or the
  `SAVEFILE`/`.sgtp` format.** `random.c` is ported bit-exact. The one
  owner-approved exception is D-025: `solo` generates a different
  `DESC` for the killer seeds that entry lists, with no parity claim
  for them; `SoloDescTest` and `SoloTest` pin it.
- **Any difference from upstream is a bug** until it is described in
  `docs/DEVIATIONS.md` and pinned by a test.
- **Game board:** the palette is part of parity. The shell theme is not.
- **No network, analytics, trackers, or new permissions** in the app
  without an ADR. Help opens only from local assets. JavaScript is
  enabled only for the activity's own style injection, not for page
  scripts (D-15).
- **Do not edit generated files by hand.** For example,
  `BackendNames.kt` is generated by `GenerateBackendsTask`.
- **Do not do drive-by refactoring, reformatting, or "improvements"
  to nearby code.** Every changed line must serve the task.
- **Do not add dependencies without an ADR.** First check whether the
  platform can do the job.
- **Do not install packages, change system settings, or use `sudo`
  without explicit permission.**
- **Do not use ASCII art in code comments or documentation.**
  ASCII tables and diagrams are hard to edit. Use Unicode
  box-drawing characters for diagrams, or plain lists and Markdown
  tables.

## Contribution policy

This repository does **not** accept commits or pull requests created
through Claude Code or any AI coding agent. Do not mention Claude or
AI assistance in commit messages, commit trailers, PR titles, or PR
descriptions. This includes `Generated with Claude`,
`Co-authored-by: Claude`, and similar lines.

## Tools

- For structural questions about the code, use **`codebase-memory-mcp`**:
  `search_graph`, `trace_path`, `query_graph`, `get_architecture`,
  `get_code_snippet`. Use `grep`/`rg` only for literals and where the
  graph does not cover the code.
- If the project index is stale, re-index it before you draw conclusions.
- External skills are not sources of truth. Before installing one,
  check the criteria in `docs/SKILLS.md`. If it fails, do not install
  it; move the useful instructions into `docs/`.
- Do not install skills that need network access, Node/Python/Playwright,
  auto-activate on general words, duplicate the docs, or have no clear
  license.
- Chat replies: short, no filler. Code, comments, commits, and docs:
  full sentences.

## Workflow

1. Read `AGENTS.md`, `docs/PARITY.md`, `docs/ROADMAP.md`, and the
   relevant ADR.
2. State the goal and a verifiable definition of done.
3. Find the code through `codebase-memory-mcp`. Check that the file is
   not vendored.
4. Make the smallest change that solves the task.
5. Run the check. Report the **evidence**: the command and its output.
6. Update tests, goldens, and docs if the change affects them.
7. If you are unsure or see a contradiction, stop and ask.

Do not report "done" until the check passes. "It looks right" is not
proof.

## Commands

Current:

```bash
./gradlew :app:assembleDebug          # build the APK
./gradlew :app:testDebugUnitTest      # JVM unit tests
./gradlew :engine:jvmTest             # portable engine tests
./gradlew :app:lint                   # Android lint
./gradlew :app:connectedDebugAndroidTest  # instrumented tests; needs a device or emulator
```

Other commands, all available today:

```bash
tools/oracle/build.sh                 # host oracle
build/oracle/puzzles-oracle            # oracle binary
./gradlew :parity:test -Poracle=build/oracle/puzzles-oracle
./gradlew :parity:test --tests '*FifteenDescTest*'
tools/gen-goldens.sh                   # regenerate goldens
tools/gen-saves.sh                     # regenerate the .sgtp corpus
```

If a command does not work, do not work around it. Fix it or report it.

## Definition of done

- Parity suite is green at the declared level (`strict`, `semantic`, `ui`).
- New behavior has a test; a fixed bug has a regression fixture.
- A new deviation is in `docs/DEVIATIONS.md` and pinned by a test.
- Accessibility: TalkBack, targets ≥ 48dp, contrast, font scale 200%.
- Ported-game input: a real tap/swipe instrumentation test, plus input
  at a non-default tile size. Drawing and input use one geometry.
- Performance: the budgets in `docs/PERFORMANCE.md` are not exceeded.
- No edits to vendored or generated files.
- Documentation is updated if rules or structure changed.

## Review and checks

- For a non-trivial diff, ask for an independent review in a fresh
  context (subagent/reviewer). Check the goal and correctness, not style.
- Checks must be deterministic: test, lint, parity, hook. Do not bypass
  them with `--no-verify` or disable them to make a change pass.
- If you have to explain the same fix twice, stop, rewrite the task,
  and rewrite the definition of done.
- In the PR or report, include evidence: what you ran, what you got,
  which files changed, and why.

## When the oracle disagrees

Do not update the golden. First find the cause:

1. a bug in our code;
2. a bug in upstream;
3. an intentional deviation.

Only the third case goes into `docs/DEVIATIONS.md`, and only with a
test that pins it.

## Language and style

- Comments and commits: **English, simple English**, en-US:
  `color`, `serialize`, `behavior`, `initialize`.
  Target about 80% of ASD-STE100: short sentences, one idea per
  sentence, no idioms, no bureaucratic wording.
- Do not rename existing upstream identifiers or public names
  (`colours`, `serialise`, `midend_serialise`, `behaviour`). They are
  part of the contract and the vendored code.
- Commit: `type(scope): imperative summary`, at most 72 characters.
  The body explains **why**.
- Documentation is in English.
- No emoji in code, commits, or documentation.
